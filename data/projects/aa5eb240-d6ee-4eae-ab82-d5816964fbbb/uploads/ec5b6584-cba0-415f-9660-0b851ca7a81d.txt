# Technical Requirements Document (TRD)
## Hotel Booking Agentic Chatbot — Backend

**Version:** 1.0  
**Date:** 2026-05-12  
**Status:** Draft

---

## 1. Overview

A backend-only agentic workflow implemented in Python. No REST API, no frontend, no UI framework. The entry point is a Python script (`main.py`) that accepts guest messages and runs the agentic workflow to completion, printing structured output to stdout. Agents are Python classes, each owning an LLM instance.

## 3. Tech Stack

| Component | Choice |
|-----------|--------|
| Language | Python 3.11+ |
| LLM client | `langchain-openai` + `openai` |
| Structured output | `pydantic` v2 — all agent boundaries |
| Embeddings (FAQ) | OpenAI `text-embedding-3-small` or `sentence-transformers` (local) |
| Vector similarity | `numpy` cosine or `chromadb` in-memory |
| Config | `python-dotenv` + `pydantic-settings` |
| Testing | `pytest` + `unittest.mock` |

## 4. Agent Design Requirements

- Every agent is a **Python class** with the LLM instantiated as an instance attribute (`self.llm`).
- A `BaseAgent` class handles shared concerns: LLM initialization, structured output binding, and log emission. All agents inherit from it.
- Each agent exposes a single public method whose input and return type are both Pydantic models. No agent method may accept or return a raw `dict` or `str` at its public boundary.
- The `OrchestratorAgent` manages conversation state (turn count, clarification count, session status) and decides which specialist agent to call next. This routing logic is pure Python — no LLM call for decisions that can be made deterministically from state.
- Agents do not call each other directly. Only the orchestrator calls specialist agents.

---

## 5. Workflow Requirements

- The workflow is a **plain Python loop** driven by the `OrchestratorAgent`. No workflow framework required.
- Each iteration: the orchestrator receives the latest guest message, inspects current state, calls the appropriate specialist agent, updates state, and either continues or terminates the loop.
- Termination conditions: booking confirmed, session escalated, or `max_turns` reached.
- Clarification rounds are capped at `MAX_CLARIFICATION_ROUNDS` (default 3). Exceeding the cap produces an `EscalationRecord`.
- Total turns are capped at `MAX_TURNS` (default 12).

---

## 6. Data Requirements

**`data/hotels.json`**
- At least 6 rooms across 3 types: `single`, `double`, `suite`.
- Each room: `room_id`, `room_type`, `price_per_night`, `max_guests`, `amenities` (list), `available_dates` (list of YYYY-MM-DD strings).

**`data/faqs.json`**
- At least 10 entries covering: check-in/out times, cancellation policy, pet policy, parking, breakfast, Wi-Fi, pool, accessibility, early check-in, late check-out.
- Each entry: `question`, `answer`, `tags`.

---

## 7. Configuration Requirements

All tuneable values must be read from environment variables (`.env` file via `python-dotenv`). No hardcoded secrets or limits in agent code.

| Env var | Default | Purpose |
|---------|---------|---------|
| `OPENAI_API_KEY` | — | Required; no default |
| `MODEL_NAME` | `gpt-4o-mini` | LLM model for all agents |
| `EMBEDDING_MODEL` | `text-embedding-3-small` | Embedding model for FAQ search |
| `MAX_CLARIFICATION_ROUNDS` | `3` | Clarification cap |
| `MAX_TURNS` | `12` | Total turn cap |
| `LOG_LEVEL` | `INFO` | Python logging level |

---

## 8. Coding Conventions

- One agent class per file; files stay under ~100 lines.
- No `print()` inside agents — use Python `logging` only.
- All LLM calls live inside agent classes; no LLM calls in `tools/`, `main.py`, or routing logic.
- Tools are stateless functions decorated with `@tool`; no instance state, no side effects beyond returning data.
- Tests mock the LLM — no real OpenAI calls in unit tests. Use `unittest.mock.patch` or `FakeListChatModel`.
- The integration test (`test_workflow.py`) runs the full orchestrator loop with pre-scripted mock LLM responses.

---

## 9. Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-01 | Single-message booking input (`"Double room Jun 10–12 for 2"`) produces a `BookingConfirmation` within 3 turns. |
| AC-02 | FAQ query (`"Do you allow pets?"`) returns a correct answer without creating a booking. |
| AC-03 | Incomplete input triggers one clarification question per turn until all required fields are gathered. |
| AC-04 | After `MAX_CLARIFICATION_ROUNDS` failures the workflow produces an `EscalationRecord` with `reason = "clarification_limit_exceeded"`. |
| AC-05 | All unit tests pass with mocked LLM calls. |
| AC-06 | No agent public method returns a raw `str` or `dict` — Pydantic models only. |
| AC-07 | `main.py` exits with a valid JSON object containing `status`, `confirmation` or `escalation`. |
